# Security Policy

## Supported versions

Security support follows the active release and evaluation branches documented in
the roadmap and release checklist.

## Reporting a security issue

If you believe you have found a security issue in the public documentation,
website, export workflow, or release packaging:

1. Do not open a public issue.
2. Use GitHub's private security advisory flow for the repository.
3. Include the affected file path, a short reproduction path, and any build or
   export evidence that helps explain the issue.

## What belongs in a security report

- Affected file path or command.
- Clear description of the risk.
- Reproduction steps if available.
- Relevant logs, hashes, or screenshots.
- Whether the issue affects public-safe, partner-only, or private material.

## What does not belong in a security report

- Customer secrets.
- Private credentials.
- Unreviewed payload fixtures.
- Nonessential implementation details.

## Response expectation

Security reports should be concise and reproducible. The goal is to assess
whether the issue affects the public-safe cut, the private implementation, or
both.
